# 经销商预约安装（#100）

## Work Packet

- 目标：经销商提交预约安装，管理员识别来源、完善订单并派单。
- 关联：#100；基线 `dev` 的 `9857765`，复用已合入的订单确认、文件和短信能力。
- 影响：后端订单、客户绑定、文件授权；小程序首页及预约表单；后台订单列表、详情、编辑和导出。
- 接口：新增经销商预约提交及任务类型查询；预约请求不接受师傅、订单状态、来源或经销商 ID。
- 数据：新增 V10 Flyway 迁移，增加来源、经销商和幂等字段，允许待派单订单无师傅；历史订单保持管理员来源。
- 验证：Maven Wrapper verify、三端角色/状态/附件/重试测试、后台生产构建和页面验证。
- 回滚：先停止预约入口，备份并处理待派单订单，再回退应用；新增列保留，不直接回滚数据库或删除申请。

## 业务契约

`PENDING_ASSIGNMENT（待派单） -> PENDING_VISIT（待上门）` 仅由管理员成功首次派单触发。待派单可作废，不能跳到处理中或已完成。管理员直接创建订单仍须指定师傅和有效时间范围。

经销商提交成功显示订单号和待派单回执；提交经销商身份不赋予客户身份或任意订单的读写权限。手机号复用已有用户，保留其角色和资料；新手机号预创建 CUSTOMER，微信授权后复用同一用户。

附件先上传为临时文件，最多 9 个，沿用统一文件服务格式与大小限制。创建订单时原子绑定本人上传且未绑定的附件。普通订单附件修改接口不向经销商开放。

客户端对同一次提交保留 requestId；服务端按经销商及 requestId 去重，同键不同内容返回 409。订单、客户、附件、状态历史及短信事件在一个事务中记录，短信发送由既有服务在事务提交后执行。

## 接口

`GET /api/v1/orders/task-types` 返回 `{code,label}[]`，仅 ADMIN/DEALER 可查询；任务编码及顺序沿用后台已有四类。`POST /api/v1/dealer/appointments` 仅 DEALER 可写，兼容去掉 `/v1` 的路径及旧的 `/mini` 路径。

提交字段：`requestId`（16–64 位字母、数字、下划线或横线）、`taskType`、必填 `description`（最多1000字）、`customerName`（1–64字）、`customerPhone`（11位，可带 +86）、`addressArea`（省市区三个非空名称）、`addressDetail`（1–500字）、可选 `fileIds`（最多9个不同的正整数）。未知字段返回400，包括师傅、状态、来源、经销商或客户用户ID。

回执为 `{id,orderNo,statusCode,orderSource}`，不会返回客户或经销商资料。管理员订单列表及详情新增 `orderSource`、`orderSourceLabel`、`dealerUserId`、`dealerName`、`dealer:{id,name,phone}`；经销商资料仅管理员响应包含。历史订单来源为 `ADMIN/管理员创建`，新预约为 `DEALER_APPOINTMENT/经销商预约`。

待派单预约可通过原 `PUT /orders/{id}` 暂不指定师傅、暂不填写时间进行修改保存；填写时间时必须提供完整有效起止时间，选择师傅后时间必填。既有 `assign-master` 入口可以在时间补齐后首次派单。重复首次派单不会重复生成指派记录和通知。管理员直接 `POST /orders` 的师傅及时间要求保持不变。

管理员更改客户手机号时重新计算绑定客户；改为未注册手机号时清除旧客户绑定，防止原客户继续看到改绑订单。客户改绑在 `operation_audit_log` 保存前后客户 ID 和脱敏手机号。

## 验证与部署

- 后端 `./mvnw.cmd verify`；小程序与后台组件 `node scripts/verify-dealer-appointment.cjs`；客户确认回归 `node scripts/verify-order-confirmation.cjs`；后台 `npm ci && npm run build`。
- 微信开发者工具与真机验收：经销商首页入口、地区选择、图片/视频上传、网络中断后重试、返回首页；其他角色首页无入口，直接打开预约页显示无权限。
- 管理员验收：原新建流程；按待派单筛选；查看来源与经销商；先保存修改再编辑派单；订单进入待上门，师傅可见，客户确认流程保留。
- V10 必须先应用再运行新版本后端。已有 V9 数据库执行增量迁移，历史订单自动标记管理员来源。

# Lczz 开发规范（一期）

## 1. 项目目标

本项目一期包含三个交付端：

- 后台管理系统：供管理员维护订单、耗材、备货和用户。
- 微信小程序：供安装师傅和客户查看、处理各自订单，同时展示产品和静态官网。
- Java 后端：为后台管理系统和微信小程序提供统一 API，使用 MySQL 持久化数据。

一期不包含线上支付、收费、经销商端、物流系统和有效的“我的”功能入口。收费继续在线下完成。

## 2. 技术边界

### 2.1 后端技术栈（已冻结）

- Java 21 LTS。
- Spring Boot 3.x。
- MySQL 8.x。
- MyBatis-Plus，业务持久层不再引入 Spring Data JPA。
- Maven，统一使用 Maven Wrapper。
- Spring Security + JWT，后台账号和小程序用户共用服务端授权体系。
- OpenAPI 3（Swagger UI）维护接口文档。
- 数据库版本管理使用 Flyway，禁止依赖手工修改数据库完成联调。
- 图片使用“文件服务适配层 + 数据库存 URL/对象键”的方式；本地开发可存本地目录，生产环境可切换对象存储。

### 2.2 前端边界

- 后台管理系统和微信小程序分别作为独立应用维护，但共享接口定义、状态枚举和基础业务术语。
- 官网为小程序内静态页面，一期不接接口。
- “产品”一期实际展示耗材，但接口和前端命名优先使用 `product`/“产品”，通过商品类型区分耗材，为后续扩展其他商品留空间。
- “我的”一期只展示个人信息；其余按钮允许展示，但不实现跳转和业务逻辑。

### 2.3 仓库目录

`dev` 是三端完整集成基线，目录固定为：

```text
backend/                  Java 后端
frontend/admin/           后台管理系统
frontend/miniprogram/     微信小程序
docs/                     项目文档
```

- 后台管理系统和小程序分别拥有自己的 `package.json`、锁文件和环境变量示例，不在仓库根目录共享前端依赖。
- 两套前端最初分别从 `release/admin`、`release/miniprogram` 以 Git subtree 方式导入，保留原提交血缘。
- 功能分支必须从 `dev` 创建，并直接修改 `frontend/admin` 或 `frontend/miniprogram` 下的源码；`release/*` 不再作为开发源分支。

## 3. 角色与权限

| 角色 | 主要权限 |
| --- | --- |
| 管理员 | 登录后台；管理订单、产品/耗材、备货和用户；指派师傅；导出订单 |
| 安装师傅 | 查看指派给自己的订单和客户联系信息；选择耗材；提交每日进度；提交完工信息 |
| 客户 | 查看由本人手机号绑定的订单；查看师傅提交的耗材、进度和完工情况；完成评价 |

权限必须由后端校验，不能只依赖前端隐藏按钮。安装师傅不得查看未指派给自己的订单，客户不得查看非本人订单。

## 4. 核心业务规则

### 4.1 注册与订单绑定

- 小程序通过微信登录并获取已验证手机号完成注册/登录。
- 后台创建订单时保存客户手机号并指派安装师傅。
- 客户首次或后续登录时，系统按标准化后的手机号查询并绑定历史未绑定订单。
- 新订单创建时，如果该手机号已有客户账号，立即绑定到该客户。
- 手机号是自动绑定依据，但数据库内部关联必须使用用户 ID，不能长期只靠手机号关联。
- 手机号变更、重复账号和订单改绑必须记录审计信息；一期仅管理员可执行改绑。

### 4.2 订单状态机

数据库与 API 使用稳定英文枚举，展示文案由前端映射：

| 代码 | 枚举 | 展示文案 | 进入条件 |
| --- | --- | --- | --- |
| 1 | `PENDING_VISIT` | 待上门 | 管理员创建并成功指派订单 |
| 2 | `IN_PROGRESS` | 处理中 | 师傅首次提交耗材申请或施工进度 |
| 3 | `PENDING_REVIEW` | 待评价 | 师傅提交完工图片和完工说明 |
| 4 | `REVIEWED` | 已评价 | 客户提交评价 |
| 9 | `CANCELLED` | 已取消 | 管理员取消订单 |

README 中代码 3 的“已完成”和“待评价”表述不一致，本规范统一为 `PENDING_REVIEW/待评价`。页面如需强调施工已完成，可显示辅助标签“施工已完成”。

状态只能按允许的路径流转：

`PENDING_VISIT -> IN_PROGRESS -> PENDING_REVIEW -> REVIEWED`

管理员取消可发生在前三个业务状态；已评价订单不可取消。删除订单采用逻辑删除，已产生耗材申请、施工记录或评价的订单不得物理删除。

### 4.3 订单字段

订单至少包含：订单编号、任务类型、省市区、详细地址、任务描述、客户姓名、客户手机号、客户用户 ID、要求时间、安装师傅用户 ID、管理员备注、状态、附件图片、创建/更新时间和逻辑删除标记。

订单编号由后端生成并保持唯一。客户手机号入库前统一格式。创建订单必须指定安装师傅；如后续确认需要“待指派”流程，再单独新增状态，不用空值隐式表达。

- 一期每张订单只允许一位当前主责安装师傅；重新指派时覆盖当前主责并保留历史指派记录，不支持同一订单多人同时施工。
- 一期任务类型采用前端现有四项：空调安装、空调维修、空调清洗、空调移机。任务类型由数据字典维护，后续新增类型不修改订单表结构。

### 4.4 施工进度与完工

- 支持一张订单多条施工进度，满足多日安装每天上传的场景。
- 每条进度包含文字说明、0 至多张图片、提交人和提交时间。
- 完工提交必须包含完工说明和至少一张图片。
- 完工后师傅不可修改已确认的耗材申请；如需调整，由管理员作废原申请后重新提交。

### 4.5 产品/耗材与备货

- 产品字段至少包含名称、分类、封面图、图集、规格/单位、描述、启用状态、排序和库存展示信息（若一期不管理真实库存，则不做库存扣减）。
- 只有启用的产品展示在小程序产品页，并可被师傅选择。
- 师傅按订单提交耗材申请，明细包含产品快照、规格、单位和数量，避免产品后来修改影响历史订单。
- 同一订单可有多次申请；后台备货以申请单为主列表，以申请明细展示耗材。
- 备货状态使用 `PENDING`（待处理）、`RECEIVED`（已领取）、`VOIDED`（已作废）。领取和作废必须记录操作人及操作时间。
- 一期不做线上支付和自动库存扣减。

### 4.6 评价

- 仅订单客户可评价，且仅 `PENDING_REVIEW` 状态允许提交。
- 每个订单只能评价一次。
- 评价包含点赞/满意标记、文字内容和提交时间；具体星级制是否启用以原型为准。

## 6. Issue 驱动开发

所有业务改动先建 Issue，再建分支和提交。GitHub Issue / PR 是开发状态和交付证据的唯一事实源。

标签采用 TTutor 的作用域形式，同一作用域只能选择一个值：

- `type::feature`、`type::bug`、`type::chore`、`type::docs`
- `status::draft`、`status::ready`、`status::in-progress`、`status::in-review`、`status::done`
- `priority::P0`、`priority::P1`、`priority::P2`、`priority::P3`

模块标签允许多选：

- `epic/admin`
- `epic/miniprogram`
- `epic/backend`
- `module/auth`
- `module/user`
- `module/order`
- `module/product`
- `module/stocking`
- `module/progress`
- `module/review`
- `module/file`

Issue 状态按以下方向流转：

`draft -> ready -> in-progress -> in-review -> done`

- `draft`：需求或验收条件尚未冻结，不得开工。
- `ready`：范围、依赖和验收标准已确认，可以认领。
- `in-progress`：已经认领并开始开发。
- `in-review`：已创建 PR，正在评审和验证。
- `done`：PR 已正确合入且验收完成。
- PR 未合入而关闭时回到 `in-progress`；验收打回时可从 `done` 回到 `in-progress`，并说明原因。不得随意跳过中间状态。

非简单改动开工前，在 Issue 评论或 PR 正文填写 Work Packet：目标、关联 Issue、影响模块/文件、接口与数据库影响、验证方式和回滚方式。

## 7. Git 分支与提交规则

日常开发流向严格为：

`feature/fix 分支 -> dev -> master`

后台管理系统和小程序需要独立上线时，使用两条发布分支：

- `release/admin`：后台管理系统及其当次配套后端的发布候选分支。
- `release/miniprogram`：微信小程序及其当次配套后端的发布候选分支。

独立发布流向为：

`feature/fix -> dev -> release/admin 或 release/miniprogram -> 部署验收 -> master`

由于 `dev` 是多工程目录，而现有 `release/admin`、`release/miniprogram` 分别以对应前端工程作为仓库根目录，发布时禁止将整个 `dev` 普通合并到 `release/*`。应从已验收的 `dev` 提交生成对应 subtree 发布分支，再发起 PR：

```bash
# 后台管理端发布候选
git subtree split --prefix=frontend/admin dev -b release-candidate/admin-<version>

# 微信小程序发布候选
git subtree split --prefix=frontend/miniprogram dev -b release-candidate/miniprogram-<version>
```

生成的候选分支分别向 `release/admin`、`release/miniprogram` 提交 PR。候选分支只用于发布同步，不得直接开发；所有修复仍从 `dev` 创建 `fix/*`，合入 `dev` 后重新生成候选分支。

`release/*` 只承担发布候选和部署，不承担日常开发。跨端共享后端变更必须先在 `dev` 完成联调，再分别合入需要该能力的发布分支；不得在两个发布分支各自修改出不同版本的共享后端。

生产稳定分支已经确定使用 `master`，默认开发分支使用 `dev`。仓库初始化时基于原 `main` 创建 `master`、`dev`、`release/admin` 和 `release/miniprogram`，将 GitHub 默认分支改为 `dev`，配置保护规则后删除原 `main`。禁止长期同时维护 `main` 与 `master` 两条生产线。

规则如下：

- `master`：生产稳定分支，只接受来自 `dev` 的 Pull Request，禁止直接提交。
- `dev`：集成分支，只接受功能/修复分支的 Pull Request，禁止直接提交。
- `release/admin`：后台独立部署分支，只接受来自 `dev` 的发布 PR；验收通过后将相同发布内容合入 `master`。
- `release/miniprogram`：小程序独立部署分支，只接受来自 `dev` 的发布 PR；验收通过后将相同发布内容合入 `master`。
- 功能分支必须从最新 `dev` 创建。
- 命名：`feature/<issue-id>-<short-name>`、`fix/<issue-id>-<short-name>`、`chore/<issue-id>-<short-name>`。
- 一个分支原则上只对应一个 Issue；前后端分别建自己的 Issue 和分支，禁止把无关改动混入。
- 禁止从功能分支直接合并到 `master`，禁止跨层级提交或合并。
- 禁止在 `release/*` 上直接提交修复；发布验收发现问题时，从 `dev` 创建 `fix/*`，修复合入 `dev` 后再同步到对应发布分支。
- 合并前同步最新 `dev` 并解决冲突；不得用强制推送改写共享分支历史。
- 每个 PR 正文必须包含且仅包含一个 Issue 关联：完整交付使用 `Closes #N`；同一 Issue 分多次交付时，中间 PR 使用 `Refs #N`，最后一个 PR 使用 `Closes #N`。
- PR 至少一人审查通过，CI 通过且获得负责人明确确认后方可合并。
- 参照 TTutor 使用 merge commit 合入，禁止 squash/rebase 合入，以保留分支与 Issue 的交付血缘。
- CI 至少检查目标分支方向、源分支命名、唯一 Issue 关联、测试、构建和密钥扫描；门禁未通过不得合并。

提交格式采用 Conventional Commits：

`<type>(<scope>): <summary> (#<issue-number>)`

示例：`feat(order): support installer assignment (#18)`。

## 8. API 与数据约定

- API 前缀统一为 `/api/v1`。
- 后台与小程序可以使用不同入口路径，例如 `/api/v1/admin/**`、`/api/v1/mini/**`，但复用同一业务服务层。
- JSON 字段使用 `camelCase`，数据库字段使用 `snake_case`。
- 时间统一以带时区语义的 ISO 8601 格式传输；数据库统一按项目约定时区存储，禁止前后端自行拼接时间字符串。
- 分页参数、响应结构、错误码、枚举和空值语义在首个接口开发前统一。
- 列表接口必须分页；搜索条件由后端白名单处理。
- 重要写操作应防重复提交；状态流转使用事务和乐观锁/版本号避免并发覆盖。
- 日志不得记录微信凭证、Token、完整手机号等敏感信息。
- 手机号返回前按角色和场景脱敏；师傅因履约需要可查看被指派订单中的客户联系方式。

## 9. 图片上传规则

- 支持的图片格式、单文件大小、单次数量在接口常量中统一，并由前后端同时校验。
- 建议一期限制为 JPEG/PNG/WebP，单文件不超过 10 MB。
- 客户端先上传文件获得文件 ID/URL，再在业务提交中引用，避免 Base64 写入 JSON 或数据库。
- 后端必须校验真实文件类型、大小和访问权限；文件名由服务端生成。
- 订单附件、施工进度、完工图片和产品图片使用统一文件表或统一文件服务，不重复实现上传逻辑。

## 10. 质量门槛与完成定义

一个 Issue 只有同时满足以下条件才可关闭：

- 功能符合原型和验收标准。
- 权限校验和异常路径已覆盖。
- 后端关键业务具有单元/集成测试，尤其是订单状态、手机号绑定、越权访问和重复评价。
- 接口文档已更新，数据库变化包含 Flyway 脚本。
- 前端无明显控制台错误，加载、空数据、失败和无权限状态均有处理。
- 图片上传在类型、大小、失败重试方面通过验证。
- PR 已审查且 CI 通过，已合并到正确的目标分支。

一期端到端验收主流程：管理员创建订单并指派师傅 -> 师傅查看订单 -> 客户手机号登录后自动看到订单 -> 师傅申请耗材 -> 后台处理备货 -> 师傅持续提交施工进度 -> 师傅提交完工 -> 客户查看并评价 -> 订单进入已评价。

## 11. 开发前待确认项

以下内容应在写业务代码前确定，并同步到原型、Issue 和接口文档：

1. 后台前端和小程序的具体技术栈及目录/仓库组织方式。
2. 管理员创建订单是否必须立即指派师傅。
3. 产品是否需要价格、真实库存、品牌、型号和多规格；一期是否只展示不售卖。
4. 耗材申请是否允许多次追加、管理员部分领取，以及领取后能否撤销。
5. 评价采用点赞、星级还是两者同时支持。

# 力创之尊一期数据库表结构审查与补全建议

## 1. 审查结论

《力创之尊数据表设计》现有 7 张表可以表达用户、产品、订单、订单耗材、完工和评价的基本轮廓，但不能直接用于一期开发。主要问题是关系型设计不足、业务状态缺失、多图片与多次施工进度无法表达、角色权限和微信身份缺失，以及多处字段类型不符合 MySQL 8 的实际语义。

建议保留现有业务概念，按本报告重新整理为 Flyway 初始化脚本，不直接照抄 Word 中的表结构建库。

## 2. 已冻结后端基线

- Java 21 LTS
- Spring Boot 3.x
- Maven Wrapper
- MyBatis-Plus
- MySQL 8.x，字符集 `utf8mb4`
- Flyway 管理全部数据库结构和基础字典数据
- Spring Security + JWT
- OpenAPI 3 / Swagger UI
- 开发环境图片可存本地文件目录，数据库只保存文件对象键和访问地址；生产通过文件服务适配层切换对象存储

开发数据库可运行在本机 MySQL，建议库名为 `lczz_dev`。本地数据库只是运行实例，提交到仓库的 Flyway SQL 才是表结构的事实源。

## 3. 原设计逐表问题

### 3.1 `t_manager_users`

必须调整：

- `type` 单值字段无法自然支持一个用户具有多个角色，建议改为用户表、角色表和用户角色关系表。
- 小程序登录缺少 `openid`、`unionid` 等微信身份字段，建议单独建立微信身份表，避免把第三方身份字段塞入用户主表。
- 密码不得使用普通 SHA-256。后台密码使用 Spring Security `PasswordEncoder`（BCrypt）；小程序用户通常不设置密码。
- `phone` 应为 `varchar(20)`，并建立标准化手机号索引；是否全局唯一需要结合“一人多角色”规则冻结。
- `last_use_time`、`create_time` 等不能使用 MySQL `TIME`，应使用 `datetime(3)`。
- 缺少账号状态、黑名单状态、删除标记、版本号、最近登录 IP/时间等字段。
- 企业名称、统一社会信用代码和公司地址不应长期重复存储在用户表。经销商公司能力进入后续版本时再拆出企业表与企业成员关系表。

### 3.2 `t_manager_menus`

该表实际表达产品/耗材分类，不是系统菜单，建议改名为 `product_category`。

应增加：分类编码、父级 ID、层级、排序、启用状态和逻辑删除字段。父级关系需要索引并防止循环引用。

### 3.3 `t_manager_material`

必须调整：

- 一期页面对外统一称“产品”，当前类型为耗材，建议表名使用 `product`。
- `material_coding` 不应为 `int64`，商品编码可能包含字母和前导零，应使用 `varchar(64)` 并唯一。
- `unit_price` 应使用 `decimal(10,2)`，不能使用 `int`。
- 缺少单位、库存展示值、启用状态、排序、主图、详情图集和逻辑删除字段。
- 多张详情图不能保存在一个字符串字段中，应通过文件关系表保存并排序。
- 一期产品不可购买，但现有前端展示价格和库存；这些字段只能作为展示信息，不产生购物车、购买、支付或库存扣减。

### 3.4 `t_manager_order`

当前缺少一期核心字段：

- 唯一订单编号
- 订单状态
- 客户用户 ID（手机号匹配后回填）
- 省、市、区编码与详细地址
- 要求上门开始时间和预计结束时间
- 管理员备注
- 作废原因、作废人和作废时间
- 乐观锁版本号与逻辑删除字段
- 多张订单附件关系

客户姓名和手机号应保留为订单快照，即使后来用户修改个人信息，历史订单也不应改变。

### 3.5 `t_order_material`

`material_ids` 把多个 ID 塞入一个字符串，违反关系型设计，无法保存数量、单位、规格快照和单项备货状态，也无法可靠查询和统计。

应拆为：

- 耗材申请单：关联订单、申请师傅、申请状态和提交时间。
- 耗材申请明细：每行一个产品，保存产品 ID、名称/编码/规格/单位快照、申请数量和备货进度。

数量建议使用 `decimal(12,3)`，以兼容冷媒等非整数耗材。

### 3.6 `t_order_completion_status`

订单可能多天施工并每天提交进度，因此“订单对应一条完成情况”的模型不成立。

建议使用施工进度表，一张订单允许多条记录，并用记录类型区分普通进度和最终完工。每条记录保存提交师傅、说明、提交时间；图片通过文件关系表保存。`completion_description` 不应唯一。

### 3.7 `t_order_comment`

必须调整：

- 评价内容不能设置唯一约束。
- 应对 `order_id` 设置唯一约束，保证每个订单只评价一次。
- 增加评价用户 ID、分数/满意标记、评价标签和评价时间。
- 评价图片使用文件关系表，不能将多图地址塞进一个字段。
- 已提交评价原则上不允许普通用户修改；管理员如需处理，只做审计留痕，不覆盖原始评价事实。

## 4. 一期建议表清单

### 4.1 账号与权限

1. `sys_user`：用户基本信息、手机号、状态、黑名单、师傅状态/备注。
2. `sys_role`：`ADMIN`、`CUSTOMER`、`INSTALLER`、`DEALER`。
3. `sys_user_role`：用户与角色多对多关系。
4. `user_wechat_identity`：小程序 `openid`、`unionid` 与用户绑定关系。

经销商一期权限等同普通用户。企业表和公司订单范围暂不创建，等订单正式需要选择公司时通过独立迁移增加。

### 4.2 数据字典

5. `sys_dict_type`：订单类型、订单状态和备货状态等字典类型。
6. `sys_dict_item`：可排序、可启停和可扩展的字典项。

### 4.3 产品

7. `product_category`：一、二级产品分类。
8. `product`：产品/耗材主数据、规格、单位、展示价格、展示库存和启用状态。

### 4.4 订单

9. `work_order`：订单主表、客户快照、绑定客户、状态、时间、地址、取消信息。
10. `work_order_assignment`：订单指派记录。一期数据库约束每单只能存在一个有效指派，并保留历史。
11. `work_order_status_history`：订单状态变更前后值、操作人、原因和时间。

### 4.5 耗材申请与备货

12. `material_request`：订单耗材申请单。
13. `material_request_item`：耗材申请明细、产品快照、数量和单项备货状态。

备货状态应能表达待备货、备货中、已备货和已作废。前端目前还支持逐项勾选，因此不能只在申请单头保存一个总状态。

### 4.6 施工与评价

14. `work_order_progress`：每日进度与最终完工记录，并约束每单只有一次最终完工提交。
15. `work_order_review`：每单唯一客户评价。

### 4.7 文件与审计

16. `file_asset`：文件对象键、原文件名、MIME、大小、存储类型和上传人。
17. `business_file_relation`：订单附件、产品图、施工图和评价图的业务关联及排序。
18. `operation_audit_log`：订单编辑、指派、作废、备货和用户状态调整等关键操作审计。

## 5. 统一字段与类型约定

- 主键统一使用 `bigint unsigned`；业务对外暴露订单编号，不直接依赖自增主键表达业务含义。
- 手机号使用 `varchar(20)`，入库前标准化。
- 金额使用 `decimal(10,2)`；数量使用 `decimal(12,3)`。
- 时间统一使用 `datetime(3)`，Java 映射为有明确时区约定的时间类型。
- 状态枚举使用稳定英文编码，接口不以中文文案作为状态值。
- 通用审计字段：`created_by`、`created_at`、`updated_by`、`updated_at`。
- 需要并发保护的表增加 `version`；可删除业务数据增加 `deleted` 或 `deleted_at`。
- 核心关系建立外键或等价的数据库约束与索引，不能只在注释中写“外键”。
- JSON 只用于确实不需要关系查询的扩展字段，不能用 JSON/逗号字符串保存 ID 列表。

## 6. 与现有前端的冲突和待冻结项

### 6.1 订单类型（已冻结）

- Word：空调安装、空调保洁、日常保洁。
- 后台前端：空调安装、空调维修、空调清洗、空调移机。

一期采用后台前端四项：空调安装、空调维修、空调清洗、空调移机。类型通过数据字典维护，后续可新增字典项，不修改订单表。

### 6.2 订单状态

- 业务规范：`PENDING_VISIT -> IN_PROGRESS -> PENDING_REVIEW -> REVIEWED`，另有 `CANCELLED`。
- 后台/小程序现有代码存在 `pending`、`processing`、`completed` 以及中文“已完成”。

数据库与 API 应以业务规范的五个稳定枚举为准，前端仅负责映射中文展示。代码 3 统一为“待评价”，可辅显“施工已完成”。

### 6.3 备货状态

- 开发规范原提议：待处理、已领取、已作废。
- 后台现有页面：待备货、备货中、已备货，并支持逐项勾选。

建议按页面行为采用 `PENDING`、`PREPARING`、`DONE`、`VOIDED`，单项保存准备数量或完成状态，申请单头保存汇总状态。

### 6.4 指派师傅数量（已冻结）

- Word 和业务描述使用单个“指派师傅”。
- 后台前端 `masterIds` 和选择表格允许一单多师傅。

一期每单仅一个当前主责师傅。`work_order.installer_user_id` 保存当前主责，`work_order_assignment` 保存历次指派记录；重新指派时旧记录失效，不允许多人同时作为有效指派。

### 6.5 前端额外能力

现有后台还出现用户黑名单/审核、产品库存、订单导出、备货逐项勾选等能力，表结构应为一期页面留出所需字段。现有“动态/资讯”页面与“小程序官网无需接口”的范围冲突，一期不为动态资讯新增数据库表，除非产品范围另行变更。

## 7. 推荐实施顺序

1. 冻结订单、备货、用户状态枚举。
2. 输出 ER 图和字段级数据字典。
3. 在后端工程创建 `V1__init_schema.sql`。
4. 创建 `V2__init_roles_and_dicts.sql`，只写角色和已冻结字典，不写演示账号密码。
5. 使用空的本地 `lczz_dev` 数据库执行 Flyway，并验证二次启动无重复建表错误。
6. 为手机号自动绑定、角色越权、订单状态流转、重复评价和备货并发补集成测试。
